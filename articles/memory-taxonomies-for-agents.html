Memory Taxonomies for Agents: Episodic, Semantic, and Procedural State in Production

One vector table called memories feels like enough right up until an agent contradicts itself, leaks one customer's history into another's session, or keeps applying a rule that a system-prompt update retired last sprint. Those are three different bugs with three different fixes, because "what an agent remembers" was never really one thing.

PUBLISHED 2026-07-26 DIFFICULTY Practitioner READ ~11 min (~1,780 words) LAB stand up a bitemporal semantic-fact store and prove stale facts expire

§1 Cold open

A support agent tells a customer, cheerfully, that their Pro-tier priority queue kicked in for the ticket they just filed. The customer downgraded to the free tier four days ago. The trace shows the retrieval step pulled a "fact" — plan: Pro — from the vector store with a similarity score of 0.91, comfortably above threshold. It's not wrong because the embedding was bad; it's wrong because the store has two rows for this customer's plan, one from four days ago and one from four months ago, and nothing in the schema ever marked either one as superseded. The agent didn't hallucinate. It retrieved real data and had no way to know which real data was current.

§2 The problem this solves — and what engineers did before it

The first generation of "agents with memory" solved recall by brute force: stuff the whole conversation history back into the context window every turn. That works until the conversation, or the relationship with a user, outlives the window — a customer who's messaged support eleven times over six months has no chance of fitting in 200K tokens of raw transcript, and even if it fit, nothing prioritizes the one fact that matters over ten turns of pleasantries.

The second generation fixed the size problem and reintroduced a correctness problem: embed every message, event, and extracted fact into one vector store, and retrieve top-k by similarity at the start of each turn. This is where most production agents sit today, and it works well enough to ship — until the store accumulates enough history that similarity search alone can't tell "this is what's true now" apart from "this was true once," or "this happened" apart from "this is a rule I should always follow." Cognitive science drew this line decades ago — Endel Tulving's split of long-term memory into episodic (events, tied to a time and place) and semantic (facts, detached from when you learned them) — and systems like MemGPT (now Letta) and mem0 rebuilt versions of that split for LLM agents because undifferentiated similarity search kept failing in exactly the way the cold open shows. The missing piece those frameworks add, and the one this article focuses on building yourself: a third category, procedural memory — the learned "how we do things here" rules that need to be versioned against the system prompt they were derived from, not just retrieved by similarity.

§3 How it actually works

Three memory types, three different invariants, three different tables — unified only at the retrieval step, not in storage:

Episodic — what happened, and when. Append-only, timestamped, never edited. "User asked to cancel order #4471 on 2026-07-20." Retrieval favors recency; nothing here is ever "current" or "stale," it just ages.
Semantic — what's true about an entity right now. Mutable, but only by superseding, never by overwrite: a fact has an effective_at and an expired_at, and updating it means closing the old row and opening a new one, so a point-in-time query is always answerable. "User's plan = Free (was Pro, changed 2026-07-22)."
Procedural — how the agent should act. A learned or authored rule, versioned alongside the system prompt it shipped with, not retrieved by similarity at all — it's either active for the current prompt version or it isn't. "Refunds over $200 require a manager-approval tool call before refund_order."

Layer 4 — data: three tables, three invariants (Postgres + pgvector)

CREATE EXTENSION IF NOT EXISTS vector;

-- Episodic: append-only, never edited, never expired.
CREATE TABLE episodic_events (
  id BIGSERIAL PRIMARY KEY,
  user_id UUID NOT NULL,
  occurred_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  content TEXT NOT NULL,
  embedding vector(1536) NOT NULL
);
CREATE INDEX ON episodic_events USING hnsw (embedding vector_cosine_ops);

-- Semantic: bitemporal. A "current" fact has expired_at IS NULL.
-- Updating a fact NEVER does UPDATE ... SET value = — it closes the
-- old row and inserts a new one, so "what did we believe on date X"
-- stays answerable.
CREATE TABLE semantic_facts (
  id BIGSERIAL PRIMARY KEY,
  user_id UUID NOT NULL,
  fact_key TEXT NOT NULL,             -- e.g. 'plan_tier', 'contact_pref'
  fact_value TEXT NOT NULL,
  embedding vector(1536) NOT NULL,
  effective_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  expired_at TIMESTAMPTZ
);
-- At most one CURRENT row per (user_id, fact_key):
CREATE UNIQUE INDEX one_current_fact
  ON semantic_facts (user_id, fact_key) WHERE expired_at IS NULL;

-- Procedural: pinned to a system-prompt version, not retrieved by
-- similarity — it's on for a version or it isn't.
CREATE TABLE procedural_rules (
  id BIGSERIAL PRIMARY KEY,
  prompt_version TEXT NOT NULL,
  rule_text TEXT NOT NULL,
  source TEXT NOT NULL              -- 'authored' | 'promoted_from_trajectory'
);

Layer 3 — agent runtime: retrieval and the write-back that keeps semantic facts honest (Python)

async def retrieve_memory(db, user_id: str, query_embedding: list[float], prompt_version: str):
    # Every query is scoped by user_id FIRST — see failure mode 1 for
    # what happens the one time this filter gets dropped in a refactor.
    episodic = await db.fetch(
        """SELECT content, occurred_at FROM episodic_events
           WHERE user_id = $1
           ORDER BY embedding <=> $2, occurred_at DESC LIMIT 5""",
        user_id, query_embedding,
    )
    semantic = await db.fetch(
        """SELECT fact_key, fact_value FROM semantic_facts
           WHERE user_id = $1 AND expired_at IS NULL""",   -- current only
        user_id,
    )
    procedural = await db.fetch(
        """SELECT rule_text FROM procedural_rules WHERE prompt_version = $1""",
        prompt_version,   -- pinned to what's deployed NOW, not similarity-matched
    )
    return {"episodic": episodic, "semantic": semantic, "procedural": procedural}


async def supersede_fact(db, user_id: str, fact_key: str, new_value: str, embedding: list[float]):
    # Expire-then-insert inside one transaction, never a bare UPDATE —
    # the unique index on (user_id, fact_key) WHERE expired_at IS NULL
    # is what makes "exactly one current row" hold under concurrent writes.
    async with db.transaction():
        await db.execute(
            """UPDATE semantic_facts SET expired_at = now()
               WHERE user_id = $1 AND fact_key = $2 AND expired_at IS NULL""",
            user_id, fact_key,
        )
        await db.execute(
            """INSERT INTO semantic_facts (user_id, fact_key, fact_value, embedding)
               VALUES ($1, $2, $3, $4)""",
            user_id, fact_key, new_value, embedding,
        )

§4 Failure modes

What you'll actually see in production
  1. The tenant filter gets dropped in a refactor. Symptom: a customer's agent session references another customer's order number or support history. The trace shows a retrieve_memory call whose SQL has no WHERE user_id = $1 clause — usually because someone "simplified" the query into a shared helper that took an optional filter, and the optional filter quietly stopped being passed. This is a multi-tenant data leak, not a quirky hallucination, and it needs the same review bar as any other cross-tenant query in the codebase.
  2. Semantic facts get overwritten instead of superseded. Symptom: the cold open — two "current" rows for the same fact_key, both retrieved, the model picking whichever scored higher on similarity that happened to be the stale one. Root cause is almost always a bare UPDATE ... SET fact_value = somewhere that bypasses the expire-then-insert path, which the unique partial index in §3 is specifically designed to make impossible if every write goes through supersede_fact.
  3. Episodic retrieval degrades as history grows. Symptom: recall latency creeps up over months, and separately, the top-k results start surfacing events that are semantically similar but months stale — "user asked about refunds" from a year-old ticket outranking last week's near-identical question because nothing in a pure cosine-similarity query accounts for recency. Left unbounded, this is also a cost problem: every turn re-embeds and re-scans a growing table for events nobody will ever need again. Fix is a recency-weighted score (blend cosine distance with age) and an archival policy, not a bigger LIMIT.
  4. Procedural memory outlives the policy it came from. Symptom: the agent enforces a manager-approval step for refunds that a system-prompt update two sprints ago replaced with an automated threshold check — support tickets show the agent blocking a refund the new policy says should go through automatically. The rule was never deleted or re-pinned to the new prompt_version, so it's still "on" for every session, silently contradicting the current system prompt because nobody versioned the two together.
Principal's Judgment Call — three-tier taxonomy vs. one memory table

Reach for the full three-tier split — separate episodic, semantic, and procedural stores with their own write invariants — when your agent maintains a relationship with a user or account across sessions that lasts weeks or months, and where a stale or duplicated fact changes what the agent tells someone: support bots, account-management agents, personal assistants. The cost of getting "what's true right now" wrong is user-facing and compounding.

Stay with a single undifferentiated memory table (or no persistent memory at all beyond the current session's rolling summary) when the agent's job is single-shot task automation with no cross-session relationship to maintain — a code-review bot, a one-off data-migration agent, anything where each run starts clean. Building bitemporal fact versioning for an agent that never needs to remember what was true last Tuesday is solving a problem you don't have.

§5 Try it in 20 minutes

LAB · Estimated 20 minutes

Mission: stand up the semantic_facts table from §3, prove that superseding a fact never leaves two "current" rows, and confirm the API layer serves only the live one.

  1. Run Postgres with pgvector locally: docker run -d --name pg -e POSTGRES_PASSWORD=pw -p 5432:5432 pgvector/pgvector:pg16, then apply the semantic_facts DDL (including the partial unique index) from §3.
  2. Insert a fact directly: INSERT INTO semantic_facts (user_id, fact_key, fact_value, embedding) VALUES ('11111111-1111-1111-1111-111111111111', 'plan_tier', 'Pro', '[...]'); (any 1536-length zero-vector works for the lab).
  3. Try to insert a second "current" row for the same user_id/fact_key without expiring the first — confirm Postgres rejects it with a unique-constraint violation on one_current_fact.
  4. Call supersede_fact from §3 (or run its two SQL statements by hand inside a transaction) to change plan_tier to Free. Confirm SELECT count(*) FROM semantic_facts WHERE user_id = '...' AND fact_key = 'plan_tier' AND expired_at IS NULL returns exactly 1.
  5. Wire up the two Express routes from §3, start the server, and hit curl localhost:3000/agent/turns/<turnId>/memory against a turn you've logged — confirm the JSON response contains only the current Free value, never the expired Pro row.
  6. Call curl -X DELETE localhost:3000/memory/semantic/<userId>/plan_tier and re-run the count query — confirm it now returns 0 current rows, proving "forget this" from the UI maps to the same expire path as a normal update.

Acceptance criteria:

  • ✅ A second unexpired insert for the same (user_id, fact_key) is rejected by the database, not caught in application code.
  • ✅ After superseding, exactly one current row exists, and the memory endpoint returns only that value.
  • ✅ The DELETE ("forget") endpoint results in zero current rows for that key, observable via the same count query.

§6 Design-review question

Staff+ interview / design-review bank

A teammate proposes collapsing all three memory types into one table — memories(id, user_id, type, content, embedding, created_at) — with a type enum instead of three tables. It's simpler to query and simpler to embed. What's wrong with it, and what would you push back with?

Strong answer sketch: the three types don't just differ in content, they differ in write invariant, and a shared schema forces a lowest-common-denominator shape that breaks at least one of them. Episodic rows are immutable and only ever appended — there's no correct notion of "expire this event." Semantic facts need "at most one current value per key," enforced by a partial unique index keyed on an expired_at IS NULL condition that has no meaning for episodic or procedural rows. Procedural rules aren't retrieved by similarity at all — they're pinned to a prompt_version, and a generic embedding-similarity query over a shared table has no way to express "only rows matching the currently deployed prompt," which is exactly the gap that produces failure mode 4. Collapsing the schema means either bolting all three invariants onto every row (episodic rows carrying an unused expired_at column, procedural rows carrying an embedding nobody queries), or — more likely — silently dropping the invariants that don't fit the common shape, which is how "current fact" and "stale fact" end up indistinguishable again. The right compromise, if a single table is a hard requirement for tooling reasons, is a shared physical table with type-specific CHECK constraints and type-specific partial indexes — not a shared invariant. But three tables unified only at the retrieval-orchestration layer, as in §3, is simpler to reason about and costs nothing at query time, since the agent runtime was always going to run three separate queries either way.
