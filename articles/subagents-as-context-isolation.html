Subagents as Context Isolation: What Never Reaches the Parent's Window

A subagent isn't mainly a way to parallelize work — it's a way to let something read 400 files, run 30 tool calls, and go down two dead ends, without a single token of that mess ever landing in the conversation the parent model actually reasons over.

PUBLISHED 2026-07-29 DIFFICULTY Practitioner READ ~10 min (~1,950 words) LAB prove the parent's context stays flat while a subagent's own persisted transcript grows

§1 Cold open

A code-migration agent is 30 turns into a session and hasn't made its first edit yet. A grep -r for a deprecated API across a monorepo returns 380 matches; the harness dutifully appends all 380 lines, and then every file the agent subsequently opens to check call sites, straight into the same message list the model reasons over on every turn. By turn 24 the agent contradicts a scoping decision it made on turn 6 — not because it changed its mind, but because turn 6 is now buried under 60,000 tokens of file dumps and grep output, and whatever attention the model has left for it has degraded. The team's first fix is a bigger context window. It buys two more days, until the same failure shows up again at 500 matches instead of 380.

§2 The problem this solves — and what engineers did before it

The instinct is to treat this as a context-window sizing problem, and windows have in fact gotten much bigger — but the failure in the cold open isn't about running out of tokens, it's about signal-to-noise inside the tokens that fit. A decision made on turn 6 is exactly as real whether it's surrounded by 5,000 tokens of unrelated file contents or 60,000; what changes is how much of the model's attention that decision has to compete for on every subsequent turn. Compaction for Long-Running Agents covers the standard answer to that once it's already happened: summarize old turns down to something smaller. But compaction is damage control — it runs after the bulky, disposable exploration has already polluted the one context the agent reasons over for the rest of the session, and every summarization pass risks losing something the next step still needed.

Before subagents were a first-class primitive, teams tried to prevent the pollution instead of cleaning it up after the fact: prompt the agent to "be concise" when grepping (unreliable — the model doesn't control how many matches a shell command returns), or run a separate offline script to pre-summarize a codebase before the agent ever sees it (rigid — it only covers queries anticipated in advance). What both approaches were reaching for, without naming it, is a boundary: some work is bulky and disposable and distills to a small answer, and that work should happen somewhere its raw output physically cannot reach the parent's context, no discipline required. A subagent is that boundary made structural. It's a fresh conversation with its own context window and its own tool access; the parent hands it a scoped brief, it does whatever exploratory work that requires — however many tool calls, however many tokens — entirely on its own, and only its final, typed return value is appended to the parent as a single message. The 380 grep matches exist; they just never enter the room where the migration decision gets made.

§3 How it actually works

The mechanism has one property that does all the work: a subagent's context starts fresh and nothing it reads or calls flows back to the parent automatically — only an explicit return value does. That means the contract on that return value is the entire interface. Get it wrong — free text instead of a schema, a summary field with nowhere to put a caveat — and isolation degrades back into the cold open's problem one level removed. FIG 3.1 traces a single delegated call across all four layers: the parent's delegate tool call, the subagent's own isolated loop, a persisted record of what the subagent actually did (kept for audit even though the parent never reads it), a progress channel the UI consumes, and an inspector card that lets a human see the isolated transcript on demand without it ever touching the main scrollback.

Layer C — agent runtime: the delegate tool and the subagent's own loop (TypeScript)

const SUBAGENT_RETURN_SCHEMA = {
  type: "object",
  required: ["files", "caveats", "confidence"],
  properties: {
    files: { type: "array", items: { type: "string" } },
    caveats: { type: "array", items: { type: "string" } }, // e.g. scope limits the parent must not ignore
    confidence: { type: "string", enum: ["high", "medium", "low"] },
  },
};

async function delegate(brief: string, allowedTools: string[]) {
  const runId = crypto.randomUUID();
  await db.query(
    `INSERT INTO subagent_runs (id, brief, status) VALUES ($1, $2, 'running')`,
    [runId, brief]
  );

  // A fresh conversation: no parent messages are copied in. The brief is
  // the *entire* starting context — that's the isolation boundary itself.
  const transcript = [{ role: "system", content: SUBAGENT_SYSTEM_PROMPT },
                       { role: "user", content: brief }];

  let result;
  while (true) {
    const step = await model.call({ messages: transcript, tools: allowedTools,
                                     response_schema: SUBAGENT_RETURN_SCHEMA });
    transcript.push(step.message);
    publishProgress(runId, { tokenCount: estimateTokens(transcript) }); // UI only
    if (step.toolCalls?.length) {
      for (const call of step.toolCalls) transcript.push(await runTool(call));
      continue;
    }
    result = step.structuredOutput; // validated against SUBAGENT_RETURN_SCHEMA
    break;
  }

  // The full transcript is persisted for audit/debugging — but it is never
  // read back into the parent's own message list. Only `result` is.
  await db.query(
    `UPDATE subagent_runs SET status = 'done', transcript = $2, token_count = $3
     WHERE id = $1`,
    [runId, JSON.stringify(transcript), estimateTokens(transcript)]
  );
  return result; // ~200 tokens, regardless of whether the subagent read 3 files or 300
}

Layer D & B — persistence and the progress channel (Postgres + SSE)

-- Extends the messages/tool_calls/agent_runs schema from
-- "Persisting Conversations and Agent State": a subagent_run is its own
-- row, linked to the parent run, but its transcript column is never
-- joined into the parent's own message-history read path.
CREATE TABLE subagent_runs (
  id UUID PRIMARY KEY,
  parent_run_id UUID NOT NULL REFERENCES agent_runs(id),
  brief TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'running', -- running | done | failed
  transcript JSONB,       -- full isolated conversation, audit-only
  token_count INT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

// This channel is deliberately separate from the parent's own token-stream
// SSE endpoint (see "Streaming Agent Output to the Browser" for the
// reconnect/backpressure mechanics that endpoint needs) — it carries
// status for a human watching the UI, and nothing here is ever read by
// the parent model.
app.get("/subagent-runs/:id/events", (req, res) => {
  res.set({ "Content-Type": "text/event-stream", "Cache-Control": "no-cache" });
  const unsubscribe = subscribeProgress(req.params.id, (evt) => {
    res.write(`data: ${JSON.stringify(evt)}\n\n`);
  });
  req.on("close", unsubscribe);
});

The frontend side is a small consumer of that channel: a collapsed card per run_id showing live token count and status, expandable on click to fetch the persisted transcript for debugging — the same shape as this session's own subagent cards, which show a final report by default and the full transcript only if you ask.

§4 Failure modes

What you'll actually see in production
  1. The return schema has nowhere to put a caveat. Symptom: the parent proceeds as if a finding applies uniformly (e.g., "the migration touches these 12 files") when the subagent's own isolated transcript — visible only if you go pull it from subagent_runs — shows it noticed the finding only holds for v2 routes. The schema's caveats field is what prevents this; a return shape with only a flat files array has no slot for that fact to survive into, so it silently doesn't.
  2. No dedup across subagent spawns. Symptom: a run's cost dashboard shows several subagent invocations with near-identical tool-call fingerprints — same grep pattern, same files opened — inside one parent session, because nothing checked whether an equivalent brief had already been answered. Isolation controls what re-enters the parent's context; it does nothing about redundant work happening in parallel disposable contexts unless the harness also caches by brief.
  3. Unschemaed, free-text returns. Symptom: intermittent parsing failures or a silently wrong file path extracted downstream, non-deterministic across otherwise-identical runs, because the parent is regex-matching a subagent's prose ("I found the migration in 3 files, located at...") instead of reading a validated field. The fix is forcing structured output on the return, not on the subagent's internal reasoning.
  4. The brief is the parent's entire transcript, not a scoped summary. Symptom: the subagent's own persisted token_count is nearly as large as the parent's would have been, and its final answer starts contradicting its own early tool calls — the exact turn-6-buried-under-turn-24 failure from the cold open, just relocated one level down. Handing over "everything, to be safe" defeats the boundary; the brief has to be a deliberately scoped statement of what the subagent needs to know, not a context dump.
Principal's Judgment Call — delegate vs. do it inline

Reach for a subagent when the work is bulky and disposable and distills to a small, typed answer — "does X exist anywhere in this repo," "read these 40 files and tell me which ones import this module," a search whose raw output the parent will never need again once it has the conclusion. The isolation is worth the round-trip precisely because what's being isolated is noise relative to the parent's actual decision-making.

Stay inline when the next step needs the full reasoning trail, not just its conclusion — a derivation the parent (or a human reviewing the trace) must audit step by step, where compressing it into a summary field would be the same information loss the schema is supposed to prevent. Also stay inline when the task is small enough that a fresh-context spawn's setup cost and latency exceed just doing the three tool calls directly; a subagent for "read one file" is machinery solving a problem you don't have.

§5 Try it in 20 minutes

LAB · Estimated 20 minutes

Mission: prove that the parent's own context size is independent of how much a delegated subagent reads, and that the isolated work is still fully recoverable for debugging.

  1. Stand up the §3 subagent_runs table and the delegate() function, with a real tool that greps a local directory of ~50 files for a string.
  2. Call delegate("find every file that imports the 'legacy-auth' module", ["grep", "read_file"]) against a small test repo where 3 files match, and record the parent transcript's token count afterward.
  3. Add 40 more files to the test repo that also match, and call delegate() again with the identical brief. Confirm the parent transcript's token count is the same as step 2 — only the subagent's own token_count in the database grew.
  4. Query SELECT token_count, transcript FROM subagent_runs ORDER BY created_at DESC LIMIT 1; and confirm the full isolated tool-call history is there even though none of it appears in the parent's own message list.
  5. Open curl -N localhost:3000/subagent-runs/<id>/events while a new delegate call runs and confirm progress events stream live, independent of the parent's own output stream.

Acceptance criteria:

  • ✅ Parent transcript token count is identical whether the subagent's matches were 3 or 43.
  • ✅ subagent_runs.transcript contains the full isolated tool-call history for later debugging.
  • ✅ The SSE progress channel emits events during a live delegate call, independently of the parent's own token stream.

§6 Design-review question

Staff+ interview / design-review bank

A teammate proposes skipping subagents and just running compaction more aggressively whenever the parent's context grows past a threshold. When is context isolation strictly better than compaction, when is compaction sufficient on its own, and would you ever want both?

Strong answer sketch: compaction and isolation solve different failure surfaces. Compaction, covered in Compaction for Long-Running Agents, is about a single agent's own accumulated reasoning history — decisions made, approaches rejected, constraints discovered — and it's lossy by construction because it summarizes real information the agent may still need. That's the right tool when the thing growing too large is the reasoning trail itself and there's no way around eventually needing a compressed version of it. Isolation is different in kind: it targets work that was never part of the reasoning trail to begin with — a bulk search, a wide read, an exploration whose raw form the parent never needed even once. Routing that through a subagent means it's never in the history compaction would later have to lossily summarize; the caveats field in the return schema is a deliberate one-time compression decision made by whoever designed the contract, not an automatic, best-effort summarization pass run under token pressure. The two compose rather than compete on a long-running session: subagents keep bulky one-off exploration out of the parent's history entirely, and compaction still has to handle the parent's own genuinely long-running reasoning thread once enough turns accumulate even with every disposable side-quest isolated out. Using compaction alone to cover for missing isolation just means the exploration's noise sat in the context for however many turns until the next compaction pass caught it — which is exactly the turn-6-buried-under-turn-24 failure the cold open describes.
