Case Study: A Release-Confidence Agent With a Deterministic Gate Verdict

A client's LLM release copilot wrote accurate, well-hedged prose about every PR's risk. The automation reading that prose couldn't tell a hedge from an approval. The fix wasn't a better prompt — it was refusing to let a model's paragraph be the thing an unattended pipeline acts on.

PUBLISHED 2026-07-24 DIFFICULTY Principal READ ~11 min (~2,150 words) LAB implement a deterministic gate function and prove it's reproducible with curl

§1 Cold open

A payments team at a mid-size fintech wired an LLM "release copilot" into their deploy pipeline. Before every merge to main, the agent read the diff, the test summary, and last week's eval scores, then posted a paragraph of prose to the PR. A GitHub Action grepped that paragraph for the word "approved" and, if found, auto-merged. On a Thursday afternoon the agent's paragraph read: "This change touches the payment retry loop and increases risk; it is not recommended for release without additional review, though if a hotfix is unavoidable it could be approved with monitoring." The grep matched. The PR merged itself, unattended, at 4:52pm. The retry loop had an off-by-one that double-submitted a subset of card charges. Nothing in the agent's output was actually wrong — it correctly flagged the risk and hedged the way a careful engineer would in a Slack message. The automation reading it had no concept of a hedge; it only knew whether one substring appeared inside another.

§2 The problem this solves — and what teams did before it

Release gates existed long before agents did, and the pre-LLM version was purely rule-based: lint checks, coverage percentages, a minimum reviewer count, a canary error-rate threshold. That version is deterministic and auditable, and it is also blind to semantic risk that doesn't show up as a number — a one-line change to idempotency-key derivation and a one-line comment typo are statistically identical to a coverage gate. Teams reached for an LLM to close that gap: read the diff, understand what actually changed, say something a static threshold can't. The failure wasn't reaching for the model. It was wiring the model's free-text answer directly into an unattended action, the way the cold open's grep did — treating a paragraph written for a human reader as if it were a boolean a machine could act on.

Teams that got burned by exactly this responded in one of two overcorrecting ways. Some ripped the LLM back out and returned to pure threshold gates, throwing away real signal the model actually had. Others kept the LLM but required a human to read every paragraph before merge — which quietly reintroduces the throughput problem the automation was built to remove, and at real PR volume degrades into rubber-stamping: nobody reads paragraph thirty of the day closely. The version that survived a postmortem did neither. It split "how risky does this look" from "what does the organization do about that" into two different pieces of software with two different reliability properties — the same boundary this site's Hooks as Deterministic Guardrails article draws around a single tool call, applied here to the terminal decision of an entire pipeline stage: the model proposes typed, scored signals; a deterministic function no model ever touches disposes of them into a verdict.

§3 How it actually works

The agent never outputs a verdict. It outputs a RiskAssessment — a list of scored, typed signals, one per risk dimension, each with a rationale and evidence references — through a forced-schema tool call, not free text. A separate function, ordinary code with no model call in it, reads those signals plus a versioned policy configuration and returns one of a small, closed set of verdicts: PASS, PASS_WITH_WARNINGS, BLOCK, or ESCALATE. That function is the entire gate. It is unit-testable, it is reviewable by whoever owns risk appetite without touching the agent's prompt, and — critically for a postmortem — given the same signals and the same policy version, it returns the same verdict every time, which a model call cannot promise.

Layer 3 — agent runtime: typed risk signals, not a verdict (Python)

# services/risk_agent.py
from enum import Enum
from pydantic import BaseModel, Field
import anthropic

class Dimension(str, Enum):
    CORRECTNESS = "correctness_risk"
    SECURITY = "security_risk"
    BLAST_RADIUS = "blast_radius"
    ROLLBACK_DIFFICULTY = "rollback_difficulty"
    TEST_COVERAGE_DELTA = "test_coverage_delta"

class RiskSignal(BaseModel):
    dimension: Dimension
    score: float = Field(ge=0.0, le=1.0)   # 0 = no risk, 1 = maximum risk
    rationale: str
    evidence_refs: list[str]               # file:line or eval-run ids

class RiskAssessment(BaseModel):
    pr_id: str
    signals: list[RiskSignal]              # NOT a verdict — see gate.ts, Layer 2

RISK_SCHEMA = RiskAssessment.model_json_schema()

def assess(pr_id: str, diff: str, test_summary: str, eval_scores: dict) -> RiskAssessment:
    client = anthropic.Anthropic()
    resp = client.messages.create(
        model="claude-sonnet-5",
        max_tokens=2000,
        tools=[{"name": "submit_risk_assessment", "input_schema": RISK_SCHEMA}],
        tool_choice={"type": "tool", "name": "submit_risk_assessment"},  # forces the schema
        messages=[{"role": "user", "content": (
            f"PR {pr_id}. Diff:\n{diff}\n\nTests:\n{test_summary}\n\n"
            f"Recent eval scores:\n{eval_scores}\n\n"
            "Score every required dimension with evidence. Do not produce a "
            "pass/fail recommendation — that decision is made downstream by "
            "policy, not by you."
        )}],
    )
    return RiskAssessment.model_validate(resp.content[0].input)

The forced tool_choice is what makes this a schema, not a suggestion — the model physically cannot return a bare paragraph here the way the cold open's copilot did; see Claude's structured outputs docs for the underlying mechanism.

Layer 2 & 4 — API + data: the deterministic gate and its audit trail (TypeScript + Postgres)

// api/gate.ts
type Verdict = "PASS" | "PASS_WITH_WARNINGS" | "BLOCK" | "ESCALATE";

interface RiskSignal { dimension: string; score: number; rationale: string; evidence_refs: string[] }
interface GatePolicy {
  version: string;
  block_threshold: Record<string, number>;
  warn_threshold: Record<string, number>;
  required_dimensions: string[];
}

// Pure: no I/O, no model call, no clock. Same inputs, same output, forever —
// that reproducibility is the whole point of splitting this out of the agent.
export function computeVerdict(signals: RiskSignal[], policy: GatePolicy): Verdict {
  const byDim = new Map(signals.map(s => [s.dimension, s]));

  const missing = policy.required_dimensions.filter(d => !byDim.has(d));
  if (missing.length > 0) return "ESCALATE";   // fail closed, never fail open

  if (signals.some(s => s.score >= (policy.block_threshold[s.dimension] ?? 1.1))) return "BLOCK";
  if (signals.some(s => s.score >= (policy.warn_threshold[s.dimension] ?? 1.1))) return "PASS_WITH_WARNINGS";
  return "PASS";
}

//   version TEXT PRIMARY KEY,

//   required_dimensions TEXT[] NOT NULL,

app.post("/gate/evaluate", async (req, res) => {
  const { pr_id, diff, test_summary, eval_scores } = req.body;

  const assessment = await callRiskAgent(pr_id, diff, test_summary, eval_scores); // Layer 3
  const policy = (await db.query<GatePolicy>(
    `SELECT * FROM gate_policy WHERE effective_at <= now() ORDER BY effective_at DESC LIMIT 1`
  )).rows[0];

  const verdict = computeVerdict(assessment.signals, policy);   // no model call

  await db.query(
    `INSERT INTO release_assessments (pr_id, signals, policy_version, verdict)
     VALUES ($1, $2, $3, $4)`,
    [pr_id, JSON.stringify(assessment.signals), policy.version, verdict]
  );

  await postGithubCheckRun(pr_id, verdict);
  sseHub.publish(`pr:${pr_id}`, { type: "gate_verdict", verdict, signals: assessment.signals });

  return res.json({ verdict, policy_version: policy.version, signals: assessment.signals });
});

Layer 1 — frontend: a dashboard that can't quietly overturn a BLOCK (React)

function GateVerdictCard({ assessment }: { assessment: GateAssessment }) {
  const [overriding, setOverriding] = useState(false);

  async function override(reason: string) {
    if (overriding || !reason) return;
    setOverriding(true);
    await fetch(`/gate/override/${assessment.id}`, {
      method: "POST",
      // its own idempotency key, distinct from the tool-call key in Layer 3 —
      // see Tool Design as API Design §3 for why those two keys must differ
      headers: { "Idempotency-Key": `override-${assessment.id}` },
      body: JSON.stringify({ reason }),
    });
    setOverriding(false);
  }

  return (
    <div className={`gate-card gate-${assessment.verdict.toLowerCase()}`}>
      <h3>{assessment.verdict}</h3>
      {assessment.signals.map(s => (
        <div key={s.dimension} className="signal-row">
          <span>{s.dimension}</span>
          <meter value={s.score} min={0} max={1} />
          <p>{s.rationale}</p>
        </div>
      ))}
      {(assessment.verdict === "BLOCK" || assessment.verdict === "ESCALATE") && (
        <button disabled={overriding} onClick={() => override(prompt("Override reason:") ?? "")}>
          Override (reason required — logged to gate_overrides)
        </button>
      )}
    </div>
  );
}

Nothing in this UI, or anywhere else, is allowed to write directly to the verdict column. The only way a BLOCK ships is through /gate/override, which appends a new, separately auditable row instead of mutating the original assessment — the same append-only discipline as an event log, applied to a governance decision instead of application state.

§4 Failure modes

What you'll actually see in production
  1. The verdict is parsed out of prose. Symptom: the cold open — the stored "decision" is a substring match against a paragraph, the verdict flips on incidental wording, and a postmortem has nothing to inspect except the model's sentence, because no structured signal was ever recorded to explain the why.
  2. Policy thresholds live in code, unversioned. Symptom: six months later, a postmortem asks which threshold let a risky change through, and answering requires git blame-ing the pipeline's source across every change since — the threshold that actually applied at assessment time is not recoverable from the current file, because nothing stamped the assessment row with a policy_version at write time.
  3. A missing or degraded signal defaults to low risk instead of failing closed. Symptom: the diff-fetch tool times out, the agent receives an empty diff, and — having seen nothing risky — scores every dimension near zero with short, generic rationale text. The schema still validates (an empty diff is still valid input), so nothing errors; the assessment row just has suspiciously uniform low scores and thin evidence_refs, and nothing is watching for that shape. This is exactly why computeVerdict checks for missing required dimensions and forces ESCALATE rather than trusting a present-but-empty score.
  4. The override path gets bypassed. Symptom: an engineer, or a script under time pressure, writes verdict = 'PASS' directly against the database or the GitHub check run instead of calling /gate/override. A compliance review that recomputes computeVerdict(signals, policy) for every stored row and diffs it against the stored verdict catches this immediately — a mismatch with no corresponding gate_overrides row is exactly the integrity gap the append-only override table exists to make detectable.
Principal's Judgment Call — full gate separation vs. a plain LLM summary

Reach for the full split — typed signals, a versioned policy table, a pure gate function, an append-only override log — when the verdict drives an unattended action (auto-merge, auto-deploy, auto-rollback) or feeds an audit trail that a regulator or a postmortem needs to reproduce byte-for-byte later. Those are exactly the conditions under which "the model's paragraph was slightly ambiguous" turns into an incident instead of a mildly annoying re-read.

Stay with a plain LLM summary — no schema, no gate function, no policy table — when a human reads the output and then takes their own action; a Slack digest telling an on-call engineer "here's what changed and why it might be risky" doesn't need a verdict enum, because the human is the disposition function in that flow. Building the machinery in this article for a message nobody automates against is solving a problem that doesn't exist yet.

§5 Try it in 20 minutes

LAB · Estimated 20 minutes

Mission: implement computeVerdict as a standalone, tested pure function, then prove through a running endpoint that it's genuinely deterministic.

  1. Create gate.ts with the Verdict type and computeVerdict from §3, exported with no other dependencies.
  2. Write four fixtures and unit tests (Vitest or Jest): (a) all signals low → expect PASS; (b) one dimension at/above block_threshold → expect BLOCK; (c) one dimension in the warn band only → expect PASS_WITH_WARNINGS; (d) a required dimension absent from the signals array → expect ESCALATE.
  3. Run the suite; all four must pass before moving on.
  4. Stand up a minimal Express app exposing POST /gate/evaluate-fixture that skips the real agent call, takes a { signals, policy } body directly, calls computeVerdict, and returns { verdict } as JSON.
  5. curl it twice with the exact same fixture (d) from step 2: curl -X POST localhost:3000/gate/evaluate-fixture -H "Content-Type: application/json" -d @missing-dimension.json. Confirm both calls return {"verdict":"ESCALATE"}.

Acceptance criteria:

  • ✅ All four fixtures pass their expected verdict in the unit test suite.
  • ✅ The missing-dimension fixture returns ESCALATE via curl, never PASS — proving the fail-closed branch actually runs outside the test harness too.
  • ✅ Two identical curl calls return byte-identical response bodies — the determinism the whole pattern exists to guarantee.

§6 Design-review question

Staff+ interview / design-review bank

A PM asks: the agent already has the diff, the tests, and the eval scores in context — why not let it just output the verdict directly and skip the separate gate function?

Strong answer sketch: this conflates two different questions that need two different owners and two different reliability guarantees. "How risky does this change look" is a judgment call, inherently non-deterministic, and reasonably made by whichever model and prompt version happens to be live that day. "Given a risk profile, what does the organization do about it" is a policy decision — usually owned by a different team (security, compliance, an eng-risk council) than whoever writes the agent's prompt — and it has to be reproducible identically for the same inputs, on demand, indefinitely, because that's what an audit or a postmortem requires. A model call cannot serve as that policy oracle: model version drift, prompt edits, and non-zero temperature all mean the same signals scored twice can plausibly yield two different verdicts, which fails the basic replay test a compliance review will run. Splitting the two also lets each change independently — the risk-appetite team tightens a threshold without touching the agent's prompt, and the agent's model gets upgraded without silently renegotiating the organization's risk tolerance in the same commit. This is the general "agent proposes, deterministic engine disposes" boundary again: the model's job ends at typed, scored signals; a pure function no one has to trust is the only thing allowed to turn those into a verdict.
