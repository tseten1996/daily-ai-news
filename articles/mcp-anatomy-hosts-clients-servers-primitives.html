MCP Anatomy: Hosts, Clients, Servers, and the Primitives That Actually Ship Code

Every team that adopts MCP treats it as "the way you give an agent a tool" for about two weeks, then hits a wall the marketing never mentioned: a second server, a third, a fourth, and suddenly nobody can say which one owns a given capability, why one hangs on stdout, or why a resource the model can clearly see never shows up in a tool call. The protocol has an actual architecture underneath the acronym. This is it.

PUBLISHED 2026-07-25 DIFFICULTY Foundations READ ~10 min (~1,850 words) LAB run a minimal MCP server and inspect its primitives over stdio

§1 Cold open

A team wires up three MCP servers into their coding agent — one for their internal ticket tracker, one for a Postgres read replica, one for their deploy pipeline — and within a day the agent starts calling get_ticket when the user asked about a deploy, and trigger_deploy when the user asked to read a ticket. Nobody wrote a routing bug; there's no router to have a bug. All three servers publish flat, generically-named tool lists into the same context window, and the model is picking the plausible-sounding one under whatever the current prompt's framing happens to favor. The team spends an afternoon assuming their harness has a wiring problem before someone actually reads the MCP spec's connection model and realizes the tools were never supposed to be indistinguishable in the first place — the protocol has a place for scoping and provenance, and nobody was using it.

§2 The problem this solves — and what engineers did before it

Before MCP (Anthropic, November 2024), every agent framework that wanted to call a ticket tracker, a database, and a deploy pipeline wrote three bespoke integrations, each with its own auth handling, its own way of describing itself to the model, and its own error-surfacing conventions. Swapping frameworks meant rewriting every integration from scratch — the classic M×N problem: M agent frameworks, N tools, no shared interface, so the integration burden grows with the product of both instead of the sum.

MCP's answer is deliberately narrow: standardize the wire protocol and the small set of primitives a tool provider can expose, and leave everything above that — how the model decides what to call, how a UI renders the result — to the host. That's the trade teams misjudge on first contact: MCP is not an orchestration framework, and it has no opinion on your agent loop. It's closer to what LSP did for editors and language servers a decade earlier — one protocol, N backends, M clients, nobody writes the cross product. Get the anatomy right and a server built for one host works unmodified in the next one; get it wrong and you've just reinvented bespoke integrations with extra JSON-RPC ceremony on top.

§3 How it actually works

Three roles, one connection rule, five primitives. The host is the application the user actually opens — a coding agent, a chat client, an IDE plugin — and it owns the LLM conversation, the UI, and which servers are even in scope this session. The host doesn't talk to servers directly; it instantiates one client per server, and each client keeps a strictly one-to-one, stateful connection to its server. That 1:1 rule is what teams skip past fastest and pay for later: it's what stops one compromised or misbehaving server from seeing traffic meant for another, and it's why a host with three servers has three separate client objects, not one client juggling three connections.

A server is a lightweight, focused process — often wrapping one existing system (a database, a SaaS API, a filesystem) — that exposes some subset of five primitives over JSON-RPC 2.0. Three live on the server side: tools (model-invoked actions with side effects, e.g. create_ticket), resources (addressable, mostly read-only context the host can attach to a conversation, each with a URI), and prompts (reusable, server-defined templates a user invokes explicitly, e.g. a slash command). Two live on the client side, which most first-time implementers miss because it inverts the direction they expect: sampling lets a server ask the host's client to run an LLM completion on the server's behalf, so a server doesn't need its own API key or model access, and roots let a client tell a server which directories or resources are actually in scope, so a filesystem server doesn't default to the whole disk. Transport is JSON-RPC 2.0 over either stdio (host spawns the server as a subprocess, talks over stdin/stdout — the default for local, trusted tools) or Streamable HTTP (for remote servers; see Streaming Agent Output to the Browser for the SSE mechanics that transport reuses).

Layer 3 — agent runtime: a minimal MCP server (TypeScript)

// npm install @modelcontextprotocol/sdk zod
import { McpServer, ResourceTemplate } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({ name: "tickets", version: "1.0.0" });

// TOOL — model-invoked, has a side effect. The description IS part of
// the prompt the model reasons over; see the failure modes below.
server.tool(
  "create_ticket",
  "Create a support ticket. Use only when the user explicitly asks " +
  "to file, log, or open a ticket — never for read-only questions.",
  { title: z.string(), body: z.string(), priority: z.enum(["low", "high"]) },
  async ({ title, body, priority }) => {
    const id = await db.insertTicket({ title, body, priority });
    return { content: [{ type: "text", text: `Created ticket ${id}` }] };
  }
);

// RESOURCE — addressable context, not a model-invoked action. The host
// decides when to attach it; the model doesn't "call" a resource.
server.resource(
  "ticket",
  new ResourceTemplate("ticket://{id}", { list: undefined }),
  async (uri, { id }) => ({
    contents: [{ uri: uri.href, text: await db.getTicketText(id) }],
  })
);

const transport = new StdioServerTransport();
await server.connect(transport);

Layer 3 — agent runtime: a host connecting to it (Python)

# pip install mcp
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

params = StdioServerParameters(command="node", args=["tickets-server.js"])

async def run():
    async with stdio_client(params) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()  # capability negotiation handshake

            tools = await session.list_tools()
            # The host, not the server, decides what reaches the model's
            # context — this is the scoping point the cold open skipped.
            visible = [t for t in tools.tools if t.name in ALLOWED_FOR_SESSION]

            result = await session.call_tool(
                "create_ticket",
                {"title": "Deploy failed", "body": "...", "priority": "high"},
            )
            print(result.content)

Layer 4 — data/infra: persisting which servers a session may see (SQL)

CREATE TABLE session_mcp_servers (
  session_id   TEXT NOT NULL,
  server_name  TEXT NOT NULL,          -- 'tickets', 'postgres-ro', 'deploy'
  connected_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  disconnected_at TIMESTAMPTZ,          -- NULL while still in scope
  PRIMARY KEY (session_id, server_name)
);

-- On resume, the host re-derives ALLOWED_FOR_SESSION from this table
-- instead of trusting whatever the client happened to connect to last —
-- a user who disconnected "deploy" mid-session must not silently regain
-- it just because the process restarted.
SELECT server_name FROM session_mcp_servers
WHERE session_id = $1 AND disconnected_at IS NULL;

Notice what each layer actually owns: the server (Layer 3, wrapped process) defines the primitive and its schema; the host's client code (also Layer 3, but the calling side) decides which of the server's advertised tools are even visible to this session's model — filtering, namespacing, and per-server tool prefixes all happen here, not in the protocol. The ALLOWED_FOR_SESSION check in the Python snippet above is exactly what that Layer 4 table backs: a production host derives it from the database on every resume, not from in-memory state that a restart would reset back to "everything visible."

§4 Failure modes

What you'll actually see in production
  1. Tool-name collisions across servers. Symptom: the cold open — the model calls the wrong server's tool, or your harness throws ambiguous tool name: run_query at startup. Two servers expose a generically-named tool and the host flattened both into one namespace without prefixing. Fix at the host: namespace every tool as {server_name}.{tool_name} before it reaches the model's context — the same discipline Tool Design as API Design argues for per-tool, applied one level up at the connection level.
  2. A resource the model "sees" never gets attached. Symptom: a user asks about a file the agent clearly listed moments ago, and the model answers as if it's never seen it. Resources are addressable, not auto-injected — resources/list tells the host what's available, but something in the host still has to explicitly call resources/read and attach the content. Teams that treat resources like tools the model can just "call" hit this immediately.
  3. Sampling requests hang or get silently dropped. Symptom: a server-side trace shows a sampling/createMessage request sent, then nothing — no error, no timeout. Most hosts don't implement sampling by default (it means letting a server spend the user's model budget), and a server that assumes otherwise hangs on a host that silently doesn't support it. Check capabilities.sampling from the initialize handshake before issuing the request.
  4. stdio server writes a stray line to stdout. Symptom: the client throws a JSON parse error on an otherwise-working server, correlated with nothing in your own code. stdio transport treats every stdout line as a JSON-RPC message — a leftover console.log, or a dependency that logs to stdout by default, corrupts the stream. Logs must go to stderr, always, for any stdio server.
Principal's Judgment Call — stdio vs. Streamable HTTP

Reach for stdio when the server and host run on the same machine, the server is trusted (you wrote it, or it ships with your own toolchain), and you want zero network surface to secure — a local filesystem server or an internal CLI wrapper are the common case. It's simpler to deploy (no auth, no TLS) and there's no network hop, but it doesn't scale past one host process and can't be shared across users or sessions.

Reach for Streamable HTTP the moment the server is remote, shared across multiple users or hosts, or needs real authentication and authorization — a company-wide ticket server or a SaaS-hosted MCP endpoint. It costs you an OAuth flow and a network dependency, but it's the only option that lets one server instance serve many hosts concurrently. Don't default to HTTP for a server only your own agent will ever call — that's paying the remote-server tax for a problem you don't have.

§5 Try it in 20 minutes

LAB · Estimated 20 minutes

Mission: run the TypeScript server from §3, connect the official MCP Inspector to it over stdio, and confirm you can see and exercise all three of its server-side primitives without writing a host at all.

  1. Save the §3 TypeScript snippet as tickets-server.js (compile or run via tsx), stub db.insertTicket/db.getTicketText to return in-memory fake data.
  2. Run npx @modelcontextprotocol/inspector node tickets-server.js — this launches a local web UI that speaks the client role of the protocol.
  3. In the Inspector's browser UI, open the "Tools" tab and confirm create_ticket appears with its full description and Zod-derived JSON schema.
  4. Call create_ticket from the Inspector with a sample payload and confirm the response content matches what your stub returns.
  5. Open the "Resources" tab, request ticket://demo-1, and confirm the resource read path works independently of the tool call — this is the resources-vs-tools distinction from failure mode 2, made concrete.

Acceptance criteria:

  • ✅ The Inspector's Tools tab lists create_ticket with the exact description string from the source, proving the description text is transmitted verbatim as protocol data, not summarized.
  • ✅ A tool call round-trips a response visible in the Inspector's history pane.
  • ✅ A resource read via ticket://{id} succeeds without going through call_tool at any point.

§6 Design-review question

Staff+ interview / design-review bank

Your team is building a host that will eventually connect to a dozen MCP servers, some internal and some third-party. A teammate proposes flattening every server's tools into one global list in the system prompt so the model has "everything available" on every turn. What breaks as the server count grows, and what would you do instead?

Strong answer sketch: three things degrade as the flat list grows. Context cost — every tool's name, description, and schema burns tokens on every turn regardless of need, and a dozen servers can easily add thousands of dead-weight tokens per request. Selection accuracy — the cold open's collision problem generalizes: the larger and more homogeneous the list, the more often the model picks a plausible-sounding wrong tool, especially across servers with overlapping domains. Blast radius — a flat list gives every session access to every server's most dangerous tool (a deploy trigger next to a read-only lookup) with no way to say "this conversation shouldn't see that." The fix is to make server selection an explicit, host-owned decision instead of an implicit one made by cramming everything into context: scope which servers connect per session or task, namespace every tool with its owning server so the model's choice is legible in a trace, and route side-effecting calls through an approval surface keyed by server identity — third-party servers face stricter human-in-the-loop gates than internal ones by default. Same principle as idempotency-key minting in Tool Design as API Design: the model should never be the one deciding what's even in scope.
