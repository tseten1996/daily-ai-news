Persisting Conversations and Agent State: Schema Design in Postgres

Every team gets fast, resumable streaming working first — an SSE channel, a Redis buffer for reconnects — and treats that as "the conversation is saved." It isn't. The moment someone needs to audit a tool call, enforce tenant isolation, or answer "what did the agent actually do" a week later, the durable system of record has to live somewhere else: a relational schema built to be queried, not just replayed.

PUBLISHED 2026-07-28 DIFFICULTY Practitioner READ ~11 min (~2,100 words) LAB seed a Postgres schema, prove cursor pagination and RLS tenant isolation with curl

§1 Cold open

Three days after closing a support ticket, a customer disputes a refund the agent "never made." An engineer pulls up the conversation to check — and there isn't one. The chat lived in the browser's local state and a 24-hour Redis stream used to replay a mid-session reconnect (see Streaming Agent Output to the Browser); neither was ever built to outlive the tab. The only surviving evidence is a row in the payments ledger with no context attached: which agent run produced it, from which turn, under whose authorization. The team had built a fast, resumable chat. They had never built a system of record.

§2 The problem this solves — and what engineers did before it

The fastest way to ship an agent chat is to keep the whole message array as one JSON value — in memory during a demo, then in a single TEXT or JSONB column on a conversations row once someone insists on "persistence." Appending a turn becomes UPDATE conversations SET messages = messages || $1 WHERE id = $2. It works, right up until two browser tabs write to the same conversation, or a retried request lands twice — then it's a classic read-modify-write race: two concurrent updates both read the same old array, both append, and whichever commits last silently erases the other's turn. Financial systems hit this exact bug with mutable ledgers decades before agents existed, which is why every accounting system since has used an append-only journal of immutable facts instead of one document everyone races to edit in place.

The other common shortcut is outsourcing state entirely to a model provider's hosted conversation API — convenient for a prototype, since there's no schema to design at all. It stops working the moment the product needs anything the vendor's thread object doesn't model: joining a conversation to your own tenant and subscription tables, enforcing row-level security per customer, or recording a tool call as a structured, auditable fact instead of a sentence buried in assistant text. A hosted thread is a cache of the conversation the provider is willing to keep; it was never meant to be your system of record.

§3 How it actually works

Treat a conversation the way an event-sourced ledger treats an account: an aggregate root (conversations) with an append-only stream of immutable facts (messages), where anything structured enough to audit or bill against — a tool invocation — gets its own first-class row (tool_calls) instead of living as prose inside a message. A separate agent_runs table tracks one row per loop invocation, holding the model, token counts, and a checkpoint pointer the harness uses to resume after a crash — the same checkpoint concept The No-Framework Option builds inside a single process, now durable across restarts. Every table carries a tenant_id path back to conversations, enforced by Postgres row-level security so a bug in one API handler's WHERE clause can't leak another customer's history — the database, not application code, is the last line of defense.

Layer 4 — data/infra: the schema (SQL)

CREATE TABLE conversations (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id   UUID NOT NULL,
  user_id     UUID NOT NULL,
  title       TEXT,
  status      TEXT NOT NULL DEFAULT 'active',
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Append-only: every row is written once via INSERT. seq is a single
-- globally monotonic identity — not reset per conversation — used purely
-- as a stable, gap-tolerant cursor for pagination and ordering.
CREATE TABLE messages (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  conversation_id UUID NOT NULL REFERENCES conversations(id),
  seq             BIGINT GENERATED ALWAYS AS IDENTITY,
  role            TEXT NOT NULL CHECK (role IN ('user','assistant','system','tool')),
  content         JSONB NOT NULL,
  status          TEXT NOT NULL DEFAULT 'complete' CHECK (status IN ('complete','failed')),
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (conversation_id, seq)
);

-- First-class, not prose inside a message. idempotency_key follows the
-- same pattern as Tool Design as API Design's harness-minted key.
CREATE TABLE tool_calls (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  message_id      UUID NOT NULL REFERENCES messages(id),
  tool_name       TEXT NOT NULL,
  arguments       JSONB NOT NULL,
  idempotency_key TEXT NOT NULL UNIQUE,
  result          JSONB,
  status          TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','ok','error')),
  started_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  completed_at    TIMESTAMPTZ
);

CREATE TABLE agent_runs (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  conversation_id UUID NOT NULL REFERENCES conversations(id),
  model           TEXT NOT NULL,
  status          TEXT NOT NULL DEFAULT 'running' CHECK (status IN ('running','complete','failed')),
  checkpoint      JSONB,              -- in-flight buffer; see no-framework harness article
  input_tokens    INT,
  output_tokens   INT,
  started_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  ended_at        TIMESTAMPTZ
);

ALTER TABLE conversations ENABLE ROW LEVEL SECURITY;
ALTER TABLE messages ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON conversations
  USING (tenant_id = current_setting('app.tenant_id')::uuid);

CREATE POLICY tenant_isolation ON messages
  USING (conversation_id IN (
    SELECT id FROM conversations WHERE tenant_id = current_setting('app.tenant_id')::uuid
  ));

Layer 3 — agent runtime: writing a turn (Python)

# pip install asyncpg
import json

async def persist_turn(pool, conversation_id, role, content, tool_calls=None):
    async with pool.acquire() as conn:
        async with conn.transaction():
            message_id = await conn.fetchval(
                """INSERT INTO messages (conversation_id, role, content, status)
                   VALUES ($1, $2, $3, 'complete') RETURNING id""",
                conversation_id, role, json.dumps(content),
            )
            for tc in tool_calls or []:
                # Same idempotency key the harness minted before calling the
                # tool (Tool Design as API Design) is reused here — a crash
                # between "tool executed" and "row persisted", followed by a
                # harness retry, hits ON CONFLICT DO NOTHING instead of a
                # second row for a refund that already happened once.
                await conn.execute(
                    """INSERT INTO tool_calls
                         (message_id, tool_name, arguments, idempotency_key, result, status, completed_at)
                       VALUES ($1, $2, $3, $4, $5, $6, now())
                       ON CONFLICT (idempotency_key) DO NOTHING""",
                    message_id, tc["name"], json.dumps(tc["args"]),
                    tc["idempotency_key"], json.dumps(tc["result"]), tc["status"],
                )
    return message_id

Layer 2 — API/transport: cursor-paginated history (TypeScript)

// GET /conversations/:id/messages?after=&limit=50
app.get("/conversations/:id/messages", async (req, res) => {
  const { id } = req.params;
  const after = Number(req.query.after ?? 0);
  const limit = Math.min(Number(req.query.limit ?? 50), 200);

  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    // req.auth.tenantId comes from the verified session, never the query
    // string — RLS enforces it below even if a handler forgets to filter.
    await client.query("SET LOCAL app.tenant_id = $1", [req.auth.tenantId]);
    const { rows } = await client.query(
      `SELECT id, seq, role, content, created_at FROM messages
       WHERE conversation_id = $1 AND seq > $2
       ORDER BY seq ASC LIMIT $3`,
      [id, after, limit]
    );
    await client.query("COMMIT");
    res.json({ messages: rows, nextCursor: rows.at(-1)?.seq ?? after });
  } finally {
    client.release();
  }
});

Layer 1 — frontend: merging persisted history with live SSE (TypeScript / React)

function useConversationHistory(conversationId: string) {
  const [messages, setMessages] = useState<Message[]>([]);
  const seenIds = useRef(new Set<string>());

  useEffect(() => {
    fetch(`/api/conversations/${conversationId}/messages?limit=200`)
      .then(r => r.json())
      .then(({ messages: initial }) => {
        initial.forEach((m: Message) => seenIds.current.add(m.id));
        setMessages(initial);
      });
  }, [conversationId]);

  // Live tokens arrive over the SSE channel from the streaming article's
  // reconnect protocol; dedup by the DB-assigned message id so a replayed
  // event after a reconnect never renders the same turn twice.
  useAgentEventStream(conversationId, (event) => {
    if (event.type === "message.complete" && !seenIds.current.has(event.message.id)) {
      seenIds.current.add(event.message.id);
      setMessages(prev => [...prev, event.message]);
    }
  });

  return messages;
}

Notice the seam: Layer 3 never talks to the frontend directly, and Layer 1 never talks to Postgres directly. The agent runtime's job ends at a committed row; the API layer's job is turning committed rows into a cursor-stable page; the frontend's job is reconciling that page against whatever live events already arrived over SSE. Each layer can be tested — and fail — independently of the others, which is the whole point of not collapsing them into one JSONB write path.

§4 Failure modes

What you'll actually see in production
  1. The mutable-JSONB race. Symptom: the message count in Postgres doesn't match the span count in your OpenTelemetry trace for the same conversation — a tool call clearly executed and clearly traced, but its turn is missing from the stored array. Two concurrent UPDATE conversations SET messages = messages || $1 statements (two tabs, or a harness retry) both read the same old array and one commits over the other. Append-only INSERT rows can't lose a write this way — there's no shared document to race over.
  2. No idempotency key on the persistence write itself. Symptom: a tool call that Layer 3's API-level idempotency key already deduplicated at the HTTP boundary (per Tool Design as API Design) still shows up twice in tool_calls, because the harness crashed after executing the tool but before committing the row, then retried the whole turn from its checkpoint. The API layer's key protects the HTTP call; the persistence layer needs its own UNIQUE constraint on the same key, or a retried write duplicates the audit trail even though the underlying refund only happened once.
  3. A forgotten tenant filter, caught by nobody. Symptom: a support engineer investigating customer A's ticket pulls up message rows belonging to customer B. Code review approved the endpoint because the WHERE conversation_id = $1 clause looked scoped — but nothing checked that the conversation itself belonged to the caller's tenant. RLS turns this from an application bug into a database-enforced invariant: without SET LOCAL app.tenant_id set to the caller's real tenant, the policy returns zero rows regardless of what the query's WHERE clause says.
  4. No cursor, full-array reads. Symptom: a long-lived support thread that's accumulated a few thousand turns starts taking seconds to load, and every SSE reconnect re-fetches the entire history instead of just what's new. Profiling points at "the LLM is slow" until someone notices the multi-megabyte JSON payload on every page load — the seq-based cursor in Layer 2 exists specifically so a reconnect (or a return visit) only pulls what the client doesn't already have.
Principal's Judgment Call — normalized schema vs. a JSONB blob

Reach for the normalized, append-only schema — separate messages, tool_calls, and agent_runs tables — the moment you need to query within a conversation: audit which tool ran and when, compute cost-per-run from token counts, enforce row-level tenant isolation, or reconcile a tool call against an external ledger by its own id. That's most production agent products the moment they leave a demo, because "what did the agent actually do" is exactly the question a support or compliance team eventually asks.

Stay with a single JSONB array column only for the narrowest case: an internal, single-tenant debugging tool with no compliance surface and nobody downstream ever querying inside a conversation. Even then, keep it in Postgres — not browser storage, not a TTL'd cache — because durability, not schema shape, is the property this article is actually about. A JSONB blob in a real database beats a perfect relational schema that only exists in a tab someone can close.

§5 Try it in 20 minutes

LAB · Estimated 20 minutes

Mission: stand up the §3 schema against a real Postgres instance, seed one conversation, and prove with curl that cursor pagination and RLS tenant isolation both actually work — not just that the endpoint returns 200.

  1. Run Postgres locally: docker run -d --name pg -e POSTGRES_PASSWORD=pw -p 5432:5432 postgres:16, then apply the full DDL from §3, including both CREATE POLICY statements.
  2. Insert one row into conversations with a known tenant_id (call it tenant-a), then use the §3 Python persist_turn function (or equivalent raw SQL) to insert a user message, an assistant message, and one tool_calls row referencing it.
  3. Run the Express handler from §3 locally (ts-node server.ts), with req.auth.tenantId hardcoded to tenant-a for this step. curl "localhost:3000/conversations//messages?limit=50" and confirm both messages come back in seq order.
  4. Re-run the same curl with after=<first message's seq> and confirm only the second message is returned — the cursor, not an offset, is doing the filtering.
  5. Change the hardcoded tenant to a random, unrelated UUID and repeat step 3's request. Confirm the response is an empty messages array — RLS blocking the read even though the conversation_id in the URL is exactly correct.

Acceptance criteria:

  • ✅ The first curl call returns exactly 2 messages, ordered by ascending seq.
  • ✅ The cursored call with after set returns exactly 1 message — the one after the cursor, not the full history.
  • ✅ The wrong-tenant call returns {"messages": [], "nextCursor": 0}, proving RLS enforces isolation independent of the URL's conversation_id.

§6 Design-review question

Staff+ interview / design-review bank

A teammate proposes dropping the tool_calls table: "the assistant message's content already describes what tool ran and what it returned, so we're duplicating data." What operational capability does the team lose, and how would you push back?

Strong answer sketch: the message content is a rendering-oriented summary the model produced, in prose it phrases however it phrases it that turn — it is not a stable, queryable fact. Without a first-class tool_calls row, you lose the ability to compute cost- or call-count-per-tool without parsing free text; you lose a place to store the persistence-layer idempotency key from failure mode 2, so a crash-and-retry has no constraint to dedupe against; you lose the ability to reconcile a specific tool invocation against an external system (a payments ledger, a ticket ID) by a stable identifier instead of a string match; and you couple the audit trail to whatever the model happened to say, which can omit a call, misdescribe an argument, or simply change wording across a prompt update — the exact drift Tool Descriptions Are Prompts warns about, now infecting your own audit log instead of just tool selection. The right framing: content is what the user sees; tool_calls is what actually happened. Collapsing them makes the audit trail only as reliable as the model's prose, which is precisely the property a system of record can't depend on.
